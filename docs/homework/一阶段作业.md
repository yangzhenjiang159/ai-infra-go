# 我对 Prefill/Decode 的理解

## Prefill
- 触发时机：开始阶段，会把输入的内容进行预处理
- 计算什么：先分词，将内容拆成一个个token, 并将token向量化，再交给transformer计算出QKV，然后放到kv cache中
- 资源特征：不同的权重大小，精度，显存消耗不同。
- 显存消耗：

## Decode
- 触发时机：prefill完成后，进行解码阶段，从kv cache中取出token的向量，交给transformer计算出输出，再将输出token向量化，再交给transformer计算出QKV，然后放到kv cache中
- 计算什么：计算从首字符开始所有可能的token概率，前面的输出整体会作为后面的输入，最终直到结束
- 资源特征：边计算，边存储
- 显存消耗：

## 为什么要有 PD 分离
- 我自己的解释（用自己的话，不要抄）：如果不先做预处理，解码阶段会重复执行之前的计算，导致现存和性能下降。分离后，decode阶段可以从kv cache很方便的拿到值，快速的进行后续的生成计算

## 一句话给外行讲清楚
- PD分离是为了减少重复计算，提高性能。好比提前把零件准备好，后续只需要按照顺序加工进行，而不是每次都从造零件开始。

# 批改（总评：60 分，及格但有两个硬伤）

## 逐条批改

### Prefill

| 你的说法 | 判定 | 说明 |
|---|---|---|
| 开始阶段预处理输入 | ✅ | 对 |
| 分词 → 向量化 → 算 QKV → 放 KV Cache | ⚠️ | 细节纠偏：**只有 K 和 V 存入 KV Cache，Q 用完即弃**。"KV Cache"存的就是这俩 |
| 资源特征：权重大小/精度/显存不同 | ❌ | **跑题了**。这是模型权重，与阶段无关。Prefill 的资源特征是：**所有 prompt token 一次性并行计算（大矩阵乘法）→ 计算密集型，GPU 算力吃满** |

### Decode

| 你的说法 | 判定 | 说明 |
|---|---|---|
| 自回归：输出作为下一步输入，直到结束 | ✅ | 核心机制对 |
| 从 KV Cache 取出向量交给 transformer | ⚠️ | 准确说法：每步只用**最新一个 token 的 Q**，与历史所有 K/V 做注意力；算出的新 K/V 再追加进 Cache |
| 计算从首字符开始所有可能的 token 概率 | ❌ | **每步只预测下一个 token** 的概率分布（对整个词表做一次 softmax），不是全序列 |
| 资源特征：边计算边存储 | ⚠️ | 太含糊。核心是：**每步只算 1 个 token，算力用不满，瓶颈是反复读整个 KV Cache + 权重 → 访存密集型（带宽瓶颈）** |

## 两处空缺：显存消耗

**Prefill 的显存消耗**：一次性为全部 prompt token 生成 KV，写入 KV Cache：

```
KV Cache ≈ 层数 × 2(K和V) × 序列长度 × 隐藏维度 × 每参数字节数
```

以 Qwen2.5-7B 为例（28 层、hidden=3584、FP16）：

```
每 token ≈ 28 × 2 × 3584 × 2B ≈ 0.4 MB
4K 长度的一条请求 ≈ 1.6 GB  ← 并发 10 条 = 16 GB，12G 卡直接 OOM
```

**Decode 的显存消耗**：每生成 1 个 token，KV Cache **线性追加 0.4MB**。输出越长吃越多——这就是"权重装得下、推理还是 OOM"的原因：**OOM 几乎都是 KV Cache 撑的，不是权重**。

## 重点纠偏：为什么 PD 分离

原解释是"避免重复计算"——**方向错了**。

事实：**不分离也不重复计算**。vLLM/SGLang 默认就是混部的，prefill 和 decode 共用同一批 GPU 和同一份 KV Cache，一次都不重算。"零件类比"描述的其实是 **KV Cache 本身**的作用（复用历史计算），这个机制有没有 PD 分离都存在。

**PD 分离的真正动机：两种工序的资源特征相反，混在一起互相踩踏**

- Prefill 是算力怪兽：一个 8K 长 prompt 进来，GPU 算力被打满几百毫秒；
- Decode 是带宽乞丐：同 batch 的其他请求每步只算一个 token，本来算力闲得很，就等读 Cache；
- 混部时：长 prompt 的 prefill **卡住整张卡**，所有正在逐字生成的请求集体停摆 → 别人的 TPOT、TTFT 全部飙升。

分离后：

1. prefill 集群堆**算力卡**，decode 集群堆**带宽卡**，各配各的硬件；
2. 两边独立扩缩容，互不干扰；
3. 代价：prefill 算好的 KV Cache 要**跨节点传过去**（GB 级）——这正是阶段四 Rust 项目 `kv-transfer-proxy` 要解决的问题。

**修正版类比（替换零件版）**：

> Prefill 像餐厅备菜：大火猛炒，一次处理一大筐（占满灶台）。
> Decode 像慢炖出锅：一道一道出，靠的是灶眼持续供火（读 Cache）。
> 备菜爆炒时整灶台被占，炖的菜全停火——所以**备菜间和炖灶分开**（PD 分离），代价是备好的料要端到灶台（KV 跨机传输）。

**修正版一句话给外行**：

> "大模型回答分两步：先读题（Prefill，狂吃算力），再逐字写答案（Decode，狂吃显存带宽）。两步脾气相反，挤在同一批 GPU 上会互相拖慢，所以拆到两拨机器各干各的——代价是要把'读题笔记'（KV Cache）传过去。"

# 追问笔记：KV 传输时序 / 显存归属 / 分离成本

> 上面是批改，下面是顺着批改继续追问后补的三块，都是面试会被追着问的点。

## 一、KV 传输发生在什么时候？——一次性交接，不是持续供数

**我原来想错的**：A 在 decode 时，B 进来做 prefill，P 集群既要算 B 的 prefill，又要持续给 A 传 KV。

**纠偏**：KV 传输是**每个请求只发生一次的交接**，卡在 prefill 结束、decode 开始那个瞬间。

```
时间 →

请求A:  [P集群: prefill A] [KV-A 一次性传输] │ [D集群: decode A 第1,2,3…步 一直到 EOS]
                                            ↑ 从这一刻起，A 和 P 集群再无关系

请求B:                              [P集群: prefill B] [KV-B 一次性传输] │ [D集群: decode B …]
```

三个连带结论：

1. B 做 prefill 时，A 的 KV **早传完了**——是过去时，不占 P 现在的资源。
2. A 在 decode 阶段每步新增的 KV，**在 D 集群本地生成、本地存**，永不回传 P。
3. 所以 **P 集群的负载 = 当前正在 prefill 的那批请求**，不随已有会话数累积。

> 唯一例外：多轮对话的新一轮，历史要重新 prefill 一次——但那仍是"第二轮的一次交接"，不是 decode 过程中持续传。

## 二、产物落到 D 集群的哪里？——必须是显存

**落点：D 实例的 GPU 显存（HBM）**，具体是预分配的 KV block pool 里的 block。

传输路径（GPUDirect RDMA）：

```
P节点 GPU 显存 → RDMA 网卡 → (可选 host bounce buffer) → D节点 RDMA 网卡 → D节点 GPU 显存
```

host 内存只是**过路**，不是落点。D 端会把这些 block 直接认领成该请求的 KV Cache。

**为什么放内存/硬盘都不行**：decode 每步要把**全部历史 KV 读一遍**。4K 上下文 ≈ 1.6 GB：

| 存储位置 | 带宽量级 | 每步读 1.6GB 耗时 |
|---|---|---|
| HBM（显存） | ~2 TB/s（H100） | **≈ 0.8 ms** ✅ |
| DRAM（PCIe Gen4 x16） | ~32 GB/s | ≈ 50 ms ❌ |
| NVMe SSD | 几 GB/s | 几百 ms ❌❌ |

TPOT 目标是几十毫秒以内，放内存光读 KV 就 50ms/步，直接炸。**这就是"decode 是访存密集"的字面含义：它必须待在显存里，只因为显存带宽比 PCIe 高三个数量级。**

工程细节：D 集群必须**先为即将到来的请求预留 block**，否则传过来没地方接。所以传输前通常有一次 D 端显存水位检查/准入。

## 三、P 集群的显存需求比 D 少吗？——不是"少"，是"花在别处"

### 先纠正前提：同长度上下文的 KV 大小两边一样

用的是同一个公式，跟阶段无关：

```
每 token ≈ 层数 × 2 × hidden × 字节数 ≈ 0.4 MB（Qwen2.5-7B, FP16）
```

P 算 4K prompt → 1.6 GB；D 收进来 → 还是 1.6 GB。

### 真正的差别是"驻留时间"，不是"大小"

| | P 集群 | D 集群 |
|---|---|---|
| KV 池角色 | **周转池**：算完就发走，block 立刻复用 | **停车场**：从进来驻留到 EOS，几十秒、几千步 |
| 单请求占用性质 | 瞬时峰值 | 持续占用 |
| 池子需要多大 | 只需容纳"同时在途"的少量请求 | 决定**最大并发数**，必须巨大 |

P 用小 KV 池 + 严格背压（池满就不接新 prefill）；D 用超大 KV 池决定并发上限。

### 反向因素：P 的显存被 activation 吃掉了

prefill 一次性并行算几千个 token，**activation 峰值极大**；decode 每步只算 1 个 token，activation 可忽略。

```
P 卡显存 ≈ 权重 + 巨大的 activation 峰值 + 很小的 KV 周转池
D 卡显存 ≈ 权重 + 可忽略的 activation + 巨大的 KV 池
```

80GB 卡算例（Qwen2.5-7B）：

| | P 卡 | D 卡 |
|---|---|---|
| 权重 FP16 | 14 GB | 14 GB |
| activation | 几十 GB（长 prompt × batch） | ~忽略 |
| KV | ~10 GB（5 条 4K 在途） | ~64 GB |
| KV 容量 | —— | 64 / 0.4MB ≈ **16 万 token** |

**结论：不是"P 显存需求少"，而是两边都可能把 80GB 用满，只是花在了不同的东西上**——P 花在 activation 峰值，D 花在 KV 池容量。

### 再叠一层：两边配的卡本来就不同

P 集群堆**算力卡**（高 FLOPS），D 集群堆**带宽 + 容量卡**（高 HBM 带宽和容量）。KV 池规模是 **D 集群选型的主轴**，不是 P 的。

外加一个变量：KV 显存按 TP 切分，实践中 P/D 并行策略常常不同（D 常用更大 TP 把 KV 池摊到多卡），但那是并行策略差异，不是阶段本质差异。

## 四、分离的固定成本：权重 ×2

| 资源 | 混部 | PD 分离 | 说明 |
|---|---|---|---|
| **模型权重** | 1 份（集群内） | **2 份** | 两边都要跑完整 transformer，各装各的 |
| **KV Cache 池** | 1 个 | **2 个** | P 小周转池 + D 大停车场 |
| KV 数据本身 | —— | 天然两份 | P 那份发完即扔，不算长期成本 |
| activation 显存 | 共享 | 两边各预留（用途不同） | P 要巨大峰值，D 几乎不要 |
| prefix cache（若有） | 1 份 | **可能 2 份** | system prompt 的 KV 两边都得 warm |

**真正凭空多出来的固定开销 = 模型权重那一份。**

算账（Qwen2.5-7B FP16，14 GB 权重）：

```
混部 8 卡 TP=8：        14 ÷ 8 = 1.75 GB/卡  → 全集群 14 GB

PD 分离 P2卡 + D6卡：   P：14 ÷ 2 = 7    GB/卡 × 2 = 14 GB
                        D：14 ÷ 6 ≈ 2.33 GB/卡 × 6 = 14 GB
                        合计 28 GB —— 权重占用翻倍
```

换 70B FP16（140 GB 权重）：

```
混部 8 卡：            140 ÷ 8 = 17.5 GB/卡
PD 分离（P2+D6）：     140 × 2 = 280 GB ÷ 8 卡 = 35 GB/卡
```

80GB 卡一半显存被权重吃掉，留给 KV 和 activation 的空间被严重压缩。

### 反直觉的设计约束

> **P 集群的卡数不能无限小——下限由"权重装得下 + activation 空间够"决定。**

prefill 的 activation 峰值本来就是显存大户，权重再占一份，P 卡数就有了硬下限。做不到"P 放 1 张卡专职做 prefill"（除非模型够小或做了激进量化）。

**所以 P:D 比例不是想怎么调就怎么调，而是有约束的优化问题。**

### 产业界怎么消化这个成本

1. **共享存储加载**：权重文件存一份在 NFS/对象存储，但加载进 HBM 后没法跨集群共享。省的是磁盘，不是显存。
2. **量化压权重**：FP16 → FP8/INT8，70B 从 140GB 压到 70GB，这个"一份"的代价直接减半。这是量化在生产上流行的原因之一。
3. **混部 + Chunked Prefill**（很多场景的真替代方案）：不分离，把长 prompt 的 prefill 切块，和 decode 交错调度。
   - 权重仍只有一份，显存成本不翻倍
   - 只能缓解踩踏，不能消除；硬件画像仍然矛盾，扩缩容也不能独立
   - 所以：**中低负载用 chunked prefill，高负载/长 prompt 场景才值得上 PD 分离**
4. **同节点内划分 P/D**：8 卡里 2 卡 P、6 卡 D，KV 走 NVLink（不走网络）。省了网络那一跳，代价是失去独立扩缩容——正好折损了 PD 分离最大的收益之一。

## 五、面试版总结：收益与代价

**收益**

1. 隔离踩踏：长 prompt 的 prefill 不再卡住别人的 TPOT/TTFT
2. 各配各的硬件：P 堆算力卡，D 堆带宽/容量卡
3. 独立扩缩容：两边按自己的负载曲线伸缩

**代价**

1. **权重 ×2**（显存固定成本翻倍，大模型上非常痛）
2. **KV 跨机传输**（GB 级、与 prefill 计算同数量级；这就是阶段四 `kv-transfer-proxy` 要解决的问题）
3. **运维复杂度翻倍**（两套集群、两套参数、配比调优、故障面变大）

**一句话**：

> PD 分离用"多一份权重显存 + 一次 KV 跨机传输"换"两种工序互不踩踏"。
> 7B 上不痛不痒，70B 上要跟量化、P 卡数下限、P:D 比例一起算总账——不是无脑拆就更好。

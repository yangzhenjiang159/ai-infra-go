# 我对 Prefill/Decode 的理解

## Prefill
- 触发时机：开始阶段，会把输入的内容进行预处理
- 计算什么：先分词，将内容拆成一个个token, 并将token向量化，再交给transformer计算出QKV，然后放到kv cache中
- 资源特征：不同的权重大小，精度，显存消耗不同。
- 显存消耗：

## Decode
- 触发时机：prefill完成后，进行解码阶段，从kv cache中取出token的向量，交给transformer计算出输出，再将输出token向量化，再交给transformer计算出QKV，然后放到kv cache中
- 计算什么：计算从首字符开始所有可能的token概率，前面的输出整体会作为后面的输入，最终直到结束
- 资源特征：边计算，边存储
- 显存消耗：

## 为什么要有 PD 分离
- 我自己的解释（用自己的话，不要抄）：如果不先做预处理，解码阶段会重复执行之前的计算，导致现存和性能下降。分离后，decode阶段可以从kv cache很方便的拿到值，快速的进行后续的生成计算

## 一句话给外行讲清楚
- PD分离是为了减少重复计算，提高性能。好比提前把零件准备好，后续只需要按照顺序加工进行，而不是每次都从造零件开始。

# 批改（总评：60 分，及格但有两个硬伤）

## 逐条批改

### Prefill

| 你的说法 | 判定 | 说明 |
|---|---|---|
| 开始阶段预处理输入 | ✅ | 对 |
| 分词 → 向量化 → 算 QKV → 放 KV Cache | ⚠️ | 细节纠偏：**只有 K 和 V 存入 KV Cache，Q 用完即弃**。"KV Cache"存的就是这俩 |
| 资源特征：权重大小/精度/显存不同 | ❌ | **跑题了**。这是模型权重，与阶段无关。Prefill 的资源特征是：**所有 prompt token 一次性并行计算（大矩阵乘法）→ 计算密集型，GPU 算力吃满** |

### Decode

| 你的说法 | 判定 | 说明 |
|---|---|---|
| 自回归：输出作为下一步输入，直到结束 | ✅ | 核心机制对 |
| 从 KV Cache 取出向量交给 transformer | ⚠️ | 准确说法：每步只用**最新一个 token 的 Q**，与历史所有 K/V 做注意力；算出的新 K/V 再追加进 Cache |
| 计算从首字符开始所有可能的 token 概率 | ❌ | **每步只预测下一个 token** 的概率分布（对整个词表做一次 softmax），不是全序列 |
| 资源特征：边计算边存储 | ⚠️ | 太含糊。核心是：**每步只算 1 个 token，算力用不满，瓶颈是反复读整个 KV Cache + 权重 → 访存密集型（带宽瓶颈）** |

## 两处空缺：显存消耗

**Prefill 的显存消耗**：一次性为全部 prompt token 生成 KV，写入 KV Cache：

```
KV Cache ≈ 层数 × 2(K和V) × 序列长度 × 隐藏维度 × 每参数字节数
```

以 Qwen2.5-7B 为例（28 层、hidden=3584、FP16）：

```
每 token ≈ 28 × 2 × 3584 × 2B ≈ 0.4 MB
4K 长度的一条请求 ≈ 1.6 GB  ← 并发 10 条 = 16 GB，12G 卡直接 OOM
```

**Decode 的显存消耗**：每生成 1 个 token，KV Cache **线性追加 0.4MB**。输出越长吃越多——这就是"权重装得下、推理还是 OOM"的原因：**OOM 几乎都是 KV Cache 撑的，不是权重**。

## 重点纠偏：为什么 PD 分离

原解释是"避免重复计算"——**方向错了**。

事实：**不分离也不重复计算**。vLLM/SGLang 默认就是混部的，prefill 和 decode 共用同一批 GPU 和同一份 KV Cache，一次都不重算。"零件类比"描述的其实是 **KV Cache 本身**的作用（复用历史计算），这个机制有没有 PD 分离都存在。

**PD 分离的真正动机：两种工序的资源特征相反，混在一起互相踩踏**

- Prefill 是算力怪兽：一个 8K 长 prompt 进来，GPU 算力被打满几百毫秒；
- Decode 是带宽乞丐：同 batch 的其他请求每步只算一个 token，本来算力闲得很，就等读 Cache；
- 混部时：长 prompt 的 prefill **卡住整张卡**，所有正在逐字生成的请求集体停摆 → 别人的 TPOT、TTFT 全部飙升。

分离后：

1. prefill 集群堆**算力卡**，decode 集群堆**带宽卡**，各配各的硬件；
2. 两边独立扩缩容，互不干扰；
3. 代价：prefill 算好的 KV Cache 要**跨节点传过去**（GB 级）——这正是阶段四 Rust 项目 `kv-transfer-proxy` 要解决的问题。

**修正版类比（替换零件版）**：

> Prefill 像餐厅备菜：大火猛炒，一次处理一大筐（占满灶台）。
> Decode 像慢炖出锅：一道一道出，靠的是灶眼持续供火（读 Cache）。
> 备菜爆炒时整灶台被占，炖的菜全停火——所以**备菜间和炖灶分开**（PD 分离），代价是备好的料要端到灶台（KV 跨机传输）。

**修正版一句话给外行**：

> "大模型回答分两步：先读题（Prefill，狂吃算力），再逐字写答案（Decode，狂吃显存带宽）。两步脾气相反，挤在同一批 GPU 上会互相拖慢，所以拆到两拨机器各干各的——代价是要把'读题笔记'（KV Cache）传过去。"
